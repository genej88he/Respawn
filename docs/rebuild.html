Respawn Rebuild

Respawn keeps backups of your game saves so you can go back in time. This page tracks rebuilding it into an app real people can install, and then adding cloud backup.

Now: Phase 1

Motivation

Why this project

The goal

Respawn is Gene's one main portfolio project for summer 2027 internships. It should show real experience building something with real users and real workloads.

  • Backend / software engineering roles
  • Systems and embedded Linux roles

The advice behind it

An Amazon engineer said the best way for an intern to stand out is to build apps with real users (friends count), learn cloud, deployments, automated testing and beta/staging stages, and practice system design by designing each project yourself.

The rules we follow

  • One finished project with real users beats several half-finished ones.
  • Never make up numbers. Resume lines come only from things we measured.
  • No emulator inside Respawn. It's a save backup tool.

App improvement logic

Why we're changing how it's built

What the app does for you stays the same. The rebuild fixes five problems that would block real users and cloud backup.

One boss for the dataToday the screen keeps the game list and Python keeps the backups, and they can disagree. The backend will handle both.
Never lose a saveRestore deletes your save before copying the backup in. If that fails halfway, the save is gone. We'll copy first, then swap.
See every errorA failed restore still says "done" today. Errors will show up on screen.
Easy for friendsToday every user needs Python installed. The new app is one language and a normal installer.
Ready for the cloudCloud backup needs one place that knows about every game and backup. That's the new backend.

    What changed in the code

    The table above is the plan. This section shows what has actually changed so far: the old code, the new code, and the system design idea behind each change.

    How the screen talks to the backend

    Least privilege: give each part only the power it needs

    What changed. The page used to have full access to your computer and called the backend however it liked. Now it gets exactly one object, window.respawn, with a short list of actions. Everything else is blocked.

    Why. The page shows things from the internet (cover art now, cloud data later). If anything bad ever loaded into it, the old setup would let it read or delete your files. Now the worst it can do is press the buttons on the menu.

    Errors

    Errors must travel back across every boundary

    What changed. Before, a failed backup or restore still looked like a success, because the result was only "whatever got printed". Now every action sends back either the data or an error message, and the page can show it.

    Why. If you can't see a failure, you can't fix it, and the user thinks their save is safe when it isn't. Sending errors as normal data is a common pattern for messages between programs.

    Checking input

    Never trust input that crosses a boundary

    What changed. The backend now checks what the page sends before doing anything with it, and refuses bad input with a clear message.

    Why. It's the same idea as checking system call arguments in a kernel: the backend can't assume the page is behaving. Tested: a 300-character message and a number both get refused with readable errors.

    Where the code lives

    Separation of concerns: one job per layer

    What changed. One file used to do everything. Now each folder has one job, in the same controller → service shape as your Spring Boot projects. Repositories (database access) arrive in Phase 2.

    Why. When each layer has one job, you can test a service without a window, swap the database without touching controllers, and find code quickly.

    One list of allowed actions

    A single shared contract between two programs

    What changed. Every action the page may ask for is written down once, with the exact shape of its answer. Both sides import this file.

    Why. If one side renames a field, the build fails right away instead of the app showing "undefined". This is why TypeScript was chosen: the same file works on both sides.

    Building the screen

    Components: build each piece once, let state drive the screen

    What changed. Instead of building HTML strings and then hunting for elements to update, the page says "here is the data" and React redraws what changed. Phase 1 has one test page; the real pages move over in Phase 3.

    Why. Cloud backup will add states like signed in, uploading and conflict. Updating the page by hand for every combination gets messy; React handles it.

    Styling

    Ship what the app needs inside the app

    What changed. Tailwind and the fonts used to download from the internet every time the app opened. Now they're installed with the app and built in, using the same colors as before.

    Why. The app looks right with no internet, starts faster, and doesn't have to trust outside servers to run code in it.

    Locking down the built page

    Defense in depth: more than one safety layer

    What changed. The built page may only run the app's own code, and links can't open new windows inside the app.

    Why. Even with the menu in place, a second layer means one mistake doesn't open everything up.

    Running and building the app

    A repeatable build: one command, same result every time

    What changed. There's now a real build: TypeScript checks both sides, then the page and backend are bundled into dist/. Development has live reload.

    Why. A build that type-checks every time catches mistakes before you run the app. It's also what CI will run on every push in Phase 4.

    Electron version

    Keep dependencies patched

    What changed. The new app uses Electron 45. The old app in ui/ still uses 41 until it's deleted in Phase 3.

    Why. One of the fixed holes would have broken the page/backend separation this phase built.

    Finding Switch saves

    Read a real binary file format

    What changed. The add-game wizard can list Switch saves by game name instead of making you find a numbered folder.

    Why. It reads the emulator's own binary index, a real systems task. It only reads save files, never games. Tested against a made-up index only, so it still needs a check with real Ryujinx data.
